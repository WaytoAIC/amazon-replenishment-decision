# 数据与输出约定

## 助手负责的后台核验

先查已授权接口和资料，核商品/单位/日期/分页、库存字段、采购至货件去重与分配。缺失不填0，送达不当可售，未下单不当供给，字段冲突不擅自归因“不同口径”。接口字段、schema、分页和计算检查由助手承担，不分派业务部门；实物、真实位置和承诺核实才分配对应角色。这些是分析保障，不作为对老板的核心异常清单；只说明其对业务判断的具体影响、补查动作与责任角色。

真实标识/响应放项目忽略目录；展示和测试报告仅用匿名代号。`.local/replenishment/scope.json`若仍为candidate_unconfirmed，不能宣称全范围分类已确认。保留取数时间、源快照、时区和不同接口截点。

## 决策需要的数据

- 需求：7/14/30/90天销量和日均、原预测及日期、新预测、活动/推广/价格与目标；断货/链接影响证据。原预测无记录则如实说缺失，不用历史均值假装原计划。
- 供应：当前真正可售、预留与不可售、各仓归属、采购/生产/未发/在途/已接收各段剩余量、原承诺与最新可售日期、正常与最快可行方案。
- 参数：正式定位/分级/生命周期、覆盖/安全/间隔定义与有效版本、批量/箱规、采购至可售分段交期、赛狐利润指标、增量费用与报价。
- 归因：运营调整记录、流量/转化/广告/价格变化、外部证据；需求传递与采购/物流执行记录。
- 动作：已有计划及人工决定、责任角色、截止、履约结果和失败后的后手，避免重复建议。

## 交付顺序：业务异常 → 计算与归因 → 协同动作

归因和供应调查按 [自主查数与归因流程](evidence-investigation.md) 先完成；部门待办只保留查数后仍需人的事项及真正的履约动作。集中问题需说明已查边界、缺失信息、影响与建议；不能把“已有数据尚未读取”包装成业务待确认。

先给业务结论和优先处理项，按商品分点，不用宽表替代解释。正常商品也简述“不需要新增/仍须跟踪什么”；不能为了展示异常而虚构风险。

每个商品使用以下六项：

1. **销量变化**：历史窗口销量/日均、原预测与新预期；幅度、持续时间、主动计划/外部变化证据。原预测缺失明确标出。
2. **风险结果与计算**：断货/滞销或双向风险；无动作情景的发生日期、缺口/过量、持续期及安全线。列公式、代入、未取整量、箱规及整箱结果、批次接续；参数未定列条件不混为正式单。
3. **归因与改善空间**：已核实事实、主要假设与替代解释；正常/可改善/需重点履约/部分不可避免，及动作后残余。最快方案未经核实就写“待核”，不能说已无解。
4. **运营动作**：具体查什么/调整什么、截止、产出及对销售/利润的影响。不得因低ROI自动减少核定需求。
5. **供应链与物流动作**：分别分点，供应链写可发货数量/日期及生产/采购方案，物流写位置/下一节点/真正可售及渠道方案；交接、后手和失约升级。不要只写“催单、跟进”。
6. **老板关注与决定**：只列需要拍板的目标/资金/权限外费用或不可避免损失、选项及最后期限；不需要则写无需拍板，不制造审批。

末尾集中列实际需要人工确认的规则/资料入口，不重复问已确认的整箱、赛狐指标来源。将“正式可批准建议/条件方案/信息不足”与“执行/调整/观察”等人工结果分开。

## 留证与复评

保存输入指纹、参数来源/状态、计算脚本与中间量、匿名结论及动作建议。真实案例数据与合成验证分开；合成例子不能冒充实际报价、渠道或业务验收。

模型建议、人工批准、实际发货/下单、实际可售和经营效果分别报告。动作落实后重算剩余缺口，保留旧版本；不能后到货抹掉先前未满足需求，不能桥接与正常订单重复抵扣。
